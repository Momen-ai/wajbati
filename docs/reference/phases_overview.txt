## 4. Regression scenarios to turn into permanent tests (all reproduced by running them against the current code, except R6/R7 which are confirmed by reading the code)

| ID | Scenario | Current (buggy) result | Required result |
|---|---|---|---|
| P1 | `POST /cart/add quantity=-5`, then checkout | order total −47, item qty −5 | 422, nothing stored |
| P1b | `quantity=abc` / `99999999` | 500 / accepted | 422 |
| P2 | `PATCH /cart/update id=99999` then `GET /cart` | 500 | 422, cart intact |
| P3 | 2 meals from 2 chefs, card | 2 orders [13, 23], both `paid`, no phone stored | card disabled; fee shown per chef; `phone` stored; payment `pending` |
| P4 | `address_id` of another user | order saved with `address = NULL` | 422 |
| P5 | Guest contact form | name/email not stored | stored + visible to admin |
| P6 | `GET /chef/meals/{id}`, `/dashboard/category/{id}`, `/dashboard/contacts/{id}/edit` | 500 | 404/405 (route removed) |
| P7 | Same user rates same meal 3×; chef rates own meal; no purchase | 4 ratings stored | 1 per user/meal; chef & non-buyer rejected |
| P8 | `PATCH /profile` with another user's phone | 500 | 422 validation error |
| P9 | Admin `PUT /dashboard/users/{id}` with `shell.php` as `image` | stored `users/<hash>.php` | 422 |
| P9b | Customer `PATCH /profile` with `shell.php` as `image` | 302, stored `chefs/<hash>.php` | 422, nothing stored |
| P10 | Chef deletes a meal that is in a completed order | 0 order items remain | order items kept (snapshot name/price) |
| P11 | Chef deletes account with customer orders; admin deletes self | orders gone; 0 admins | blocked / anonymized; last admin protected |
| P12 | `User instanceof MustVerifyEmail` | false | true; unverified user can't checkout |
| P13 | Admin lists with >15 rows | no page links | page links present, `?page=2` works |
| Q8 | 8 registrations in a row from one IP | all succeed | 429 after limit |
| Q9 | Meal price 5→500 after add-to-cart, then checkout | charged 5 + fee | charged 500 + fee (or rejected with "price changed") |
| R4 | Chef orders own meal | order created | forbidden |
| R5 | Card order, chef rejects | `payment_status` stays `paid` | `failed`/`refund_pending`; excluded from revenue |
| R6 | Cash order delivered | `payment_status` stays `pending` forever | becomes `paid`; included in revenue |
| R7 | Mail transport throws during checkout | order rolled back, raw exception shown | order stored, mail queued/reported, generic message |

## 5. Definition of done

- `php artisan test` green on SQLite and MySQL; `vendor/bin/pint --test` clean; larastan level 6 clean; CI green.
- Every F-xx finding is marked **Fixed / Won't fix (with reason) / Deferred (with reason)** in `docs/REFACTOR_REPORT.md` with: files changed, migration names, tests added.
- Every stream passed an independent reviewer sub-agent, and Phases 0 and 1 also passed the red-team agent; the report lists, per stream: branch, owner agent, files, tests (RED→GREEN evidence), reviewer verdict.
- The report states which skills were really used (Superpowers: plans in `docs/plans/`, review notes; Impeccable: `docs/ui-review/*-before|after.md`) — or why a fallback was used.
- Fresh clone → follow README only → app boots with Arabic RTL UI, images visible, queue processing, zero third-party CDN requests, no PHP-executable uploads possible, no default credentials.
- Manual smoke script in the report: register → verify email → add 2 meals from 2 chefs → checkout (cash) → chef accepts → prepares → delivers → payment marked paid → customer rates → admin sees correct revenue.
